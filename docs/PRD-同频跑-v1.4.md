## 1. 产品概述

### 1.1 一句话定位

**LGBTQ 专属的同城跑步社区**：用自己习惯的 App 跑步，跑完回到同频跑打卡，在一个安全的空间里被同类看见、被回应、约到能一起跑的人。

两层含义，缺一不可：

1. **专属** —— 社区成员默认共享一个身份前提，"不用解释自己"是这里的核心价值，也是区别于任何泛跑步 App 的唯一壁垒。
2. **跑步优先** —— 连接发生在跑道上、发生在汗水和配速里，不是发生在滑卡和私聊里。**区别于单纯的线上社交**，是这一定位的另一半。

### 1.2 双层表达原则（本产品最重要的设计约束）

「专属」必须被**感受到**，但不必被**写在脸上**。产品采用双层表达：

| 层级 | 面向 | 表达 | 原因 |
|---|---|---|---|
| **外层**（可被微信生态/陌生人看见） | 小程序名称、简介、搜索词、分享卡片、**小程序备案名** | **完全中性**：只有跑步、场次、距离、城市。不出现任何社群标签词（含 pride） | 过审需要；更关键的是——用户的手机可能被任何人瞥见，分享卡片可能落到任何群里。Pride 进备案名 = 永久留在备案记录中 |
| **内层**（社区成员进入后） | 站内品牌抬头「欢迎来 同频跑 pride running 🌈」、头像体系、社区氛围、线下活动、鼓励文案、成就命名、品牌便签 | **明确的归属感与彩虹语言**，让成员一眼知道"这是自己人的地方" | 专属感来自氛围和准入，不来自标语 |

> 一句话：**外层让陌生人看不懂，内层让同类一眼认出。** 这不是妥协，而是对"未出柜用户"最基本的保护——它同时解决了合规与安全两个问题。

**命名分层（v2.4 ADR-002 定稿）**：

| 层面 | 看到的是 | 说明 |
|---|---|---|
| 工商公示 / 营业执照 | 同频跑 | 执照不得含外文；「同频跑」自带语义，用户搜得到、记得住 |
| 小程序名与备案 | 同频跑（pride running 不进备案名，倾向保守方案，最终提交前拍板） | 若进备案，Pride 永久留在记录中 |
| 站内 | 同频跑 pride running 🌈 | 圈内身份表达，可被用户一键收起（便签开关） |

> ⚠️ 商标动作：「同频跑」属描述性组合，**显著性弱、注册难度高于臆造词**。应对：尽早检索并提交 9（软件）/ 41（文体活动）/ 35（广告）类；**把彩虹跑者 Logo 单独申请图形商标**（图形不受描述性限制，本案最有效的保护手段）；Logo 做著作权登记兜底。

### 1.3 核心循环

跑步 → 打卡 → 被回应 → 发现场次/跑友 → 一起跑（**优先线下**）→ 再次跑步

### 1.4 与 Keep / 悦跑圈 / 泛跑步 App 的本质区别

| | 它们 | 同频跑 |
|---|---|---|
| 卖什么 | 记录工具 | **归属感 + 被陪伴** |
| 记录 | 核心能力 | 交给用户已有的 App（见第 7 章） |
| 社交 | 附加功能 | **产品本体** |
| 人群 | 所有跑者 | 特定人群，共享身份前提 |
| 成功指标 | 日活、里程 | **线下同跑发生的次数** |

### 1.5 明确不做的事（v1）

- ❌ 不自研 GPS 轨迹记录（纯小程序后台定位不可靠）
- ❌ 不做"附近的人"式米级地理位置曝光（只到城市粒度）
- ❌ 不做私信（合规风险 + 骚扰风险，评论区 + 鼓励足够）
- ❌ 不做精确跨用户配速排行榜（防作弊 + 调性）
- ❌ 不做滑卡 / 匹配 / 颜值导向的任何机制（与"跑步优先"定位冲突）
- ❌ 不自动拉取微信头像与昵称（见第 9 章）
- ❌ 不考虑商业化

#### 4.1.1 数据口径：「同场开跑」是约定，不是实测（重要，v2.2 修订）

UI v1.10 曾用「此刻有 128 位跑友正在奔跑」——但纯小程序**没有任何实时在线数据源**，这个数字是假的；v1.3 的状态机推导修好了"假"，但"此刻"二字仍在暗示我们能看见谁在跑——**我们看不见，也承诺永远不去做**（ADR-001）。

**v2.2 定稿口径：**

```
「本时段 X 位跑友和你同场开跑」
  = 加入了「开跑时间落在同一整点时段」场次的去重报名人数
  当前时段无场次时，取最近一场未开跑场次所在时段
```

| 展示 | 口径 | 为什么 |
|---|---|---|
| Hero 主数字「本时段 X 位和你同场开跑」 | 同一时段场次报名人数（**约定**，非实测） | 保住陪伴感，且**不谎称实时** |
| 场次卡上的「正在跑 X」 | 状态机推导：已加入 AND now ∈ [开始, 开始+宽限期] AND 未打卡 AND 未退出 | 单场数据，继续由场次推导，**不再上首页** |
| 统计条「今日 X 人完成」 | 当日累计打卡人数 | 累计口径，真实且够大 |

**口径诚实条款（强制）**：凡展示「同场开跑」数字，**必须在同一视野内写明推算方式**（Hero 常驻小字 + 关于页完整说明）。承诺不实时定位，就要说到做到——懂行用户或审核员一眼看穿的口径，一次失信就再也救不回来。

### 4.2 去跑（核心 Tab：场次 + 打卡）

**性质变更说明**：由于不自研记录，本 Tab 不是"记录页"，而是「**场次 + 打卡页**」。

**A. 场次（与你同行的落地形态）**

- 场次 = 一次异步同跑约定：`周六 9/12 07:30 · 深圳湾公园 · 5KM · 配速 5'30–6'30 · 8 人已加入`
- 用户点「加入本场」→ 到点各自用任意 App 跑 → 跑完回来打卡
- 场次页显示：**本场 8 人已加入 / 3 人已完成打卡 / 5 人正在跑**（全部由状态机推导，无需实时定位）
- 任何人可创建场次；官方每天固定发起 1 场「同频跑之夜 20:00」保证兜底
- 两类发起动作严格分开：**陪跑场次**（一次性：距离 / 时间 / 集合点 / 配速 / 人数上限 / 线上异步 or 线下约跑）与 **队伍**（长期小圈子：队伍名 / 常跑距离 / 时段 / 入队方式）

**A2. 发起表单：时间与距离输入（v1.10）**

| 字段 | 输入方式 |
|---|---|
| **时间** | 三种并存：① 顶部自由文本（可写「周六傍晚 6 点半」）② 横向滚动快捷 chip（今晚 20:00 / 21:00 / 21:30、明早 06:00 / 06:30、周六 07:00 / 18:00、周日 07:00）③ 三列滚动选择器（日期 7 天 / 时 05–23 / 分 5 分钟粒度），实时预览「周六 9/12 07:30 开跑」 |
| **距离** | 备选 3 / 5 / 8 / 10 / 15 / 半马 21.1 KM 横向滚动 ＋ 任意自定义（支持小数，如 7.5 / 12.86）；填自定义后备选取消高亮并提示「已使用自定义距离 X KM」，清空即恢复 |

- 数据落库统一走 `kmValue()`，保证**场次标题 / 详情页目标 / 打卡目标**三处一致
- 自由文本解析失败时降级为选择器，不阻塞提交

**A3. 取消与退出机制（v1.8，v2.4 修订）**

| 角色 | 能力 | 约束 |
|---|---|---|
| 发起人 | 可见「报名的人」卡片（人数 / 已打卡数 / 每人加入时间与打卡状态）；可「解散这场陪跑」 | **取消是发起人的义务，不是权利**（v2.4 修订）：确认弹层必须写明「已报名的 N 位跑友会收到通知」；取消后**必须向全部报名者推送站内消息**，不能只让场次凭空消失；全场置灰、显示「已取消」、按钮禁用 |
| 参加者 | 可「取消参加」（去跑页 + 我的页「我报名的活动」均可） | **退出后其他人看不到「已退出」记录**（避免社交压力），可随时重新加入；退出不发通知、无痕迹 |

**发起即邀请（v2.1 修订）**：发起成功后**直接打开邀请页**（太阳码 / 站内邀请，带真实场次参数），而不是丢一个 toast 结束。冷启动期"发起后无人报名"是最大流失点——邀请必须成为发起的默认动作。

**A4. 提醒：微信订阅消息（v1.7）**

- 发起面板默认开启「开始前 1 小时 · 微信订阅消息」，**用选择器选完时间即自动订阅**
- 场次详情「提醒」卡可分别订阅 **开始前 1h** 与 **本场结束**
- 活动取消时向全部报名者推送通知
- **约束**：订阅消息需**逐次授权**，一次订阅对应一场；由云函数在开跑前 1 小时定时触发
- 这条同时是**打卡漏斗的召回手段**——跑完时人往往在户外、小程序已被杀

**B. 打卡流程（录入成本必须 ≤ 15 秒，v1.11 修订）**

1. 选择已加入的场次（或"自由跑"）
2. 填距离：**收敛为 5 / 10 / 半马 21.1 三个常用 chip**，其余走「其他距离」弹窗（快捷 3/8/15/30 + 任意自定义含小数）——减少随手乱填，不损失自由
3. 填时长，**三种方式并存**（v1.10）：① 快捷 chip（15/30/45/60/90 分）② 手输 时:分:秒 三段（冒号预置、输满自动跳格、可只填分秒）③ 三列滚动选择器——三处写的是同一份数字，互相同步
4. **配速防错（v1.11）**：不评价快慢——慢不拦（跑走结合是正当需求，>18 分/km 给一句温和确认）；快到不可能才是输入错误：<3 分/km 提醒「接近专业水平，确认没填错？」，<90 秒/km **硬拦截**
5. 可选：上传成绩卡截图 → OCR 自动回填（见 7.3，v1 建议先不上）；打卡位置（一次性定位）；一句话感受
6. 授权读取微信运动步数做交叉校验（仅本地提示，不作公开质疑）

**存储约定**：时长统一存**总秒数**（`duration_s`），展示层再格式化为 `1:12:05`；配速由总秒数与距离实时计算，不单独存储。

**C. 打卡成功页**

- 主文案：「今天，你又向前了一点。」
- 数据：5.23 KM / 29:31 / 5'38"/KM
- 社交层：「🌈 今天与你同场奔跑的还有 7 位跑友」+ 头像列表
- 操作：分享这次奔跑 / 去看动态

### 4.3 跑友（社交核心，四个入口）

**概念定义（重要）**：v1.1 起区分两个对象——

- **队伍（Team）**：持久跑团，有固定成员和常规跑步时间，队长可发起约跑
- **场次 / 活动（Session）**：一次性约跑，有具体时间和目标距离，可挂在队伍下或独立发起

**四个入口的落地方式**

| 入口 | 位置 | 实现方式 | 可行性与约束 |
|---|---|---|---|
| ① 发起组队 | 右下角悬浮 ＋按钮 | 表单：队伍名 / 常跑距离 / 跑步时段 / 可见范围 / 入队方式 → 生成队伍 | ✅ 完全可行；需做频率限制防刷（如每天 ≤ 3 个） |
| ② 加入队伍 | 队伍卡片主按钮 | 写 `team_members`；队长可改为审核制 | ✅ 完全可行；这是唯一允许用户进群的路径，不做"打招呼" |
| ③ 邀请 | 队伍详情 / 队伍卡 | ① `<button open-type="share">` 分享小程序卡片（带 `scene` 参数）② 调用 `wxacode.getUnlimited` 生成**带参太阳码**存图发给朋友 | ✅ 可行；⚠️ 微信不允许静默指定发送对象，必须由用户在会话列表中选；⚠️ 分享文案不得含诱导词汇 |
| ④ 搜索 | 顶部搜索栏 + 右上角 icon | 云开发 DB 模糊查询（`db.RegExp`）；分「活动 / 跑友 / 队伍」三档 | ✅ 可行；⚠️ 数据量大后需引入 ES / 云向量检索；⚠️ 跑友搜索加「允许被搜索」开关（默认开、可关） |

**页面结构（自上而下）**

1. 搜索栏 → 点击进入搜索页，三档切换
2. 筛选 chips：跑步时段 / 常跑距离 / 周频次
3. 附近的队伍（同城列表）：队伍名 + 成员数 + 常规时间 + 下次约跑 + 「加入队伍」「邀请」
4. 推荐跑友：头像 + 昵称 + 常跑距离 + 本周次数 + 时段标签（**不展示精确配速**）+ 「一起跑」

**边界**：无私信、无打招呼、无好友关系；所有社交动线收敛到「队伍」和「场次」。

### 4.4 动态

- 内容三类型：**打卡动态**（打卡自动生成，带数据卡）/ 感受（纯文字）/ 约跑邀请（带场次卡）
- 互动：**「鼓励」**（替代点赞，icon 自绘不用 emoji）+ **评论**（v2.0 落地：每条动态展示最近 2 条，可发评论；过 msgSecCheck；**被屏蔽/屏蔽我的人不能评论**——否则评论区成了绕过屏蔽的通道）
- 每条动态「···」= **举报（两步流）/ 双向屏蔽**（v2.0 修订：举报先选分类——垃圾营销 / 人身攻击 / 骚扰不当互动 / 泄露隐私 / 其他——再补一句选填说明，给处理人上下文）
- 点作者头像 → **跑友主页**（见 4.7）
- 默认展示同城内容流（尊重作者「动态不进同城流」开关，见 9.9）；顶部可切「关注的人」
- 冷启动期由运营保证每天 3–5 条

### 4.5 我的

- 身份区：头像（生成式色块 / 用户主动换的微信头像）/ 昵称 / 跑者等级（按累计打卡次数）/ 改昵称入口
- 数据区：累计距离 / 累计次数 / 最长单次（来自打卡记录，非 GPS）
- **我报名的活动**（v1.13）：全部已加入场次列表 + 状态标签（已完成 / 我发起的 / 已报名）+ **取消参与**（无痕迹，不发通知）
- **我的记录**（v2.0）：最近 20 次打卡列表（距离 / 时长 / 配速 / 城市 / 一句话 / 日期），全部真实数据
- 我的足迹：点亮的城市地图（v1 只有深圳）
- 成就：第一次打卡 / 连续 7 天 / 累计 100KM / 第一次约跑成功 / 点亮第一座城市…
- 设置与隐私（含应用锁、性别自填、城市切换、「我们保存了什么」清单、安全中心入口、关于页入口）

### 4.6 消息中心（v2.0 新增）

**五类消息，每类带可就地完成的内联操作**——「消息只能看」的列表用户很快学会无视：

| 类型 | 触发 | 内联操作 |
|---|---|---|
| 鼓励 | 有人给动态点加油（同一条 24h 内**聚合成一条**，不刷屏） | 👋 回一个加油 |
| 报名 | 有人加入我发起的场次（附当前人数） | 查看报名的人 |
| 约跑 | 被邀请加入场次 | 🤝 接受并加入 |
| 取消 | 我报名的场次被发起人解散 | 看看其他场次 |
| 提醒 | 开跑前 1 小时（订阅消息联动） | 去这场看看 |

**硬规则**：

- **只保留 30 天**（写在列表底部，是承诺也是自律）
- **隐私相关消息（举报结果等）不显示对方任何可识别信息**——服务端就把 target 剥掉，不靠前端自觉
- 消息数据只能本人读（云函数按 openid 过滤）；入口 = 首页铃铛，未读红点
- 恶意刷消息的防护：同一条动态的鼓励聚合、退出不通知、通知写入失败不影响主流程

### 4.7 跑友主页（v2.0 新增）

- 数据全部来自云函数 `search` 的 profile 档（跨用户读取只能走云函数）；入口：动态头像、搜索跑友结果
- 内容：头像 / 昵称 / 城市 / 性别（仅当对方愿意说）/ 近 30 天 KM 与次数 / 最近 3 条动态
- **可见性全部尊重**：双向屏蔽 → 当作不存在；隐身中 / 可见范围「隐身」→ 明说「TA 关闭了主页」（不是 404——假装页面不存在会让人以为 App 在删人）；「仅互相加油过的人」→ 不在白名单同上
- **只有两个动作：屏蔽、举报。没有关注、没有私信**——连接发生在跑道上，不在收件箱里；收件箱是下一个要解释一百遍的隐私噩梦，v1 不做
- 页面上不展示精确配速（与全站口径一致）

### 4.8 首次进入流程（v2.3 重构，v2.4 品牌定稿）

**流程**：欢迎页 → 勾选同意 → 三步引导 → 进首页 → 品牌便签浮出。

**欢迎页「我们为你做的事」**（从 v2.1 的"风险告知"重构而来）：

- 标题：**欢迎来同频跑 pride running 🌈 / 这里只有跑得开心这件事。开始之前，想先告诉你三件我们为你做的事**
- 三张柔和色承诺卡（珊瑚红 / 暖琥珀 / 柔绿）：🔒 你的位置只属于你（只在主动点时读一次 / 不追踪 / 不记轨迹）｜🎭 你是谁由你决定（默认生成式 / 不自动读微信资料）｜🌿 跑你自己的节奏（不排名 / 不比配速）
- **勾选是进入的前置条件**（「好，我知道了 —— 也同意《隐私政策》与《社区规范》」）；未勾选点击按钮给一句人话提示
- **法律条款一句未删**：运动风险与免责、未成年人提示缩为底部小字——合规未削弱，只是不再抢视线
- **承诺即事实**：卡片说的每一条都必须已写进代码（位置一次性、身份默认生成、无排行），做不到的不写

**三步引导**：① 一个人跑，也不算一个人跑（异步同行 / 无滑卡无私信无人能定位你）② 三步加入一场陪跑（与 v1 实际能力一致，**没接 OCR 就不提自动识别**）③ 你的安全是默认设置（四条防线）

**引导完成后**：品牌便签延迟浮出一次（见 4.1），可在设置里永久关闭或重看。**首进只出现一次**，老用户不打扰。

## 6. 数据模型（云开发集合）

> 标注：`?` = 可选；`#` = v1.3 新增字段。

```
users        { _id, openid, nickname, avatar, city, level, created_at,
               avatar_seed?, blocked_ids#[]?,
               avatar_file_id#?,          // 用户主动选用微信头像（云存储 fileID，空=生成式）
               gender#?,                  // 'male'|'female'|'nonbinary'|'unspecified'（默认）
               visible_scope#?,            // 'city'|'cheered'|'hidden'（默认 city，见 9.9）
               ghost_until#?,              // 隐身到期时间戳，0=未隐身
               allow_feed#?,               // 动态是否进同城流（默认 true）
               allow_cheer#? }            // 陌生人能否互动（默认 true）
checkins     { _id, user_id, date, distance_km, duration_s, pace_auto,
               session_id?, screenshot_url?, note?,
               source: 'manual'|'ocr', ocr_confidence#,
               city#, step_cross_check?, created_at }
sessions     { _id, creator_id, team_id?, city, title, start_time, target_km,
               pace_range, capacity, status, is_official,
               mode#: 'online'|'offline',
               poi_name#?, poi_address#?, poi_lat#?, poi_lng#?,
               grace_minutes#: 90, status: 'open'|'cancelled',
               created_at# }
teams        { _id, owner_id, city, name, usual_km, run_window,
               visibility: 'city_public', join_mode: 'free'|'approval',
               member_count, qr_scene }
team_members { _id, team_id, user_id, role: 'owner'|'member', joined_at }
session_members { _id, session_id, user_id, joined_at, checkin_id?,
                  remind_1h#: bool, remind_end#: bool,
                  left_at#? }
posts        { _id, user_id, type: 'checkin'|'feeling'|'invite',
               checkin_id?, session_id?, content, images[],
               visibility#: 'community'|'public',
               cheer_count, comment_count, created_at }
cheers       { _id, target_type: 'post'|'checkin', target_id, from_user }
comments     { _id, post_id, user_id, text, created_at }
city_stats   { city, date, runner_count, total_km }
achievements { _id, user_id, code, unlocked_at }
reports#     { _id, reporter_id, target_type: 'user'|'post', target_id,
               reason, status: 'pending'|'resolved', created_at, handled_at? }
messages#    { _id, user_id,            // 收件人 openid，只有云函数能读
               type: 'cheer'|'join'|'invite'|'cancel'|'remind'|'comment'|'privacy',
               title, content, actor_nick?,
               target_type?, target_id?,  // privacy 类一律为空（界面承诺不显示对方信息）
               count,                     // 聚合条数（鼓励 24h 聚合）
               read: bool, created_at }
```

**关键约束**

- `duration_s` 一律存**总秒数**，展示层格式化为 `1:12:05`；配速实时计算，不单独存储
- `session_members.left_at` 用于实现「取消参加不公开已退出」——查询时排除有 `left_at` 的记录，且不向他人暴露该字段
- `users.blocked_ids` 为**双向**屏蔽：查询信息流、场次、推荐、跑友主页时，需同时排除 `A.blocked_ids 含 B` 与 `B.blocked_ids 含 A`（见 9.4）。**屏蔽同时封堵评论**——被屏蔽的人不能评论，否则评论区成了绕过屏蔽的通道
- 「正在跑」**不落库**，由 `session_members` + `sessions.start_time` + `grace_minutes` + `checkin_id` 实时推导，**只用于场次卡**（见 4.1.1）
- `messages` 只保留 30 天（可加定时清理任务）；privacy 类消息服务端剥掉 target，前端无法显示对方信息
- 可见性字段（`visible_scope` / `ghost_until` / `allow_feed` / `allow_cheer` / `searchable`）**必须在所有跨用户读路径强制执行**（search / feed / interact / profile）——写了开关不执行等于骗用户（见 9.9）

## 7. 跑步数据来源与第三方授权（调研结论）

### 7.1 结论先说

**在「纯微信小程序」这一层，几乎拿不到任何官方运动数据授权。** 原因不是接口不存在，而是：**所有健康/运动数据的开放都是给原生 App 的，小程序沙箱访问不到系统健康数据**。

### 7.2 各家可行性核对

| 数据源 | 是否可授权 | 现实条件 |
|---|---|---|
| **Keep** | ❌ 不行 | 无官方开放 API。网上流传的 `api.gotokeep.com` 属逆向抓包，违反其服务条款、随时失效，商业产品不可用 |
| **咕咚 Codoon** | ⚠️ 理论可行，门槛极高 | 有 OpenAPI + OAuth 2.0，但**不开放自助申请**，须邮件商务对接（apidata@codoon.com）评估；公开套餐为「授权 1 万账户 / 全年 10 万次访问」起，收费合作 |
| **Garmin** | ⚠️ 理论可行，门槛极高 | 需 Garmin Developer Program 审批：法人主体（**不接受个人申请**）、企业域名邮箱、公开隐私政策；审批 1–4 周；OAuth 1.0a + 推送式回调，需常驻 HTTPS 服务 |
| **Apple 健康 / 华为 HiHealth / Zepp / 小米穿戴** | ❌ 小程序不行 | 均为原生 SDK（HealthKit / Health Connect），小程序无法调用；若未来做原生 App 则可打通 |
| **Strava** | ⚠️ 可行但用户少 | 官方 OAuth API 开放，但国内用户基数小 |
| **微信运动** | ✅ 可用但很弱 | `wx.getWeRunData` 仅提供**步数**，无距离/配速，只能做起量级交叉校验 |

### 7.3 v1 采用的方案：曲线达标——截图 OCR 自动回填

```
用户在 Keep / 咕咚 / 手表 App 里跑完
  → 保存官方跑步成绩卡片到相册
  → 同频跑「打卡」页上传图片
  → wx.chooseMedia → 云存储 → 云函数调用 OCR（腾讯云通用印刷体识别）
  → 正则提取「距离 / 时长 / 配速」→ 回填表单，用户一键确认
```

- 把录入时间从 15 秒压到 **5 秒**，接近自动同步的体感
- 不需要任何第三方授权、不涉及 ToS 风险、零商务成本
- 成本：OCR 调用几分钱/次，只在用户主动上传时发生

**交互三态（v1.9）**：上传后显示「正在识别成绩卡…」→ 成功则展示识别结果卡（缩略图 + 距离 / 时长 / 平均配速 + **置信度**）并自动回填；提供「重新识别」。

**版式适配与降级（v1.9 补充）**

| 项 | 约定 |
|---|---|
| 首批支持版式 | Keep / 咕咚 / 悦跑圈 / Apple Watch 四家成绩卡，做成**版式适配层**（每家一组正则 + 坐标策略），新增 App 只加配置不改主流程 |
| 已知难点 | 配速/时长格式混排（`52:14` 与 `5'13"` 同名不同义），必须按版式区分解析，不能通用正则 |
| 置信度阈值 | 低于阈值**自动降级为手输**，并提示用户「没看清，麻烦手填一下」——不阻塞流程 |
| 埋点 | 记录 版式 / 置信度 / 成功或失败 / 用户是否手动修正，**失败率纳入每周复盘** |
| **冷启动期建议** | **v1 先不上 OCR**，纯手输 + 备选距离 chip。适配成本远大于收益，省下精力投到线下场景；等打卡量稳定后再按埋点数据决定先适配哪两三家 |

### 7.4 后续演进路标

| 阶段 | 方案 | 触发条件 |
|---|---|---|
| v1（现在） | 手输 + 截图 OCR + 微信运动步数校验 | — |
| v1.5 | 接入 Strava OAuth 试点 | 有海外端用户反馈需求 |
| v2 | 若有**公司主体**：申请 Garmin Health API / 咕咚商务合作 | 用户量或营收达到能覆盖商务成本 |
| v2.5 | 若做原生 App：直连 HealthKit / Health Connect / 华为 HiHealth | 社区成立、需要完整数据能力 |

> 这也是「先做小程序验证社区、再决定是否做 App」这条路线的核心价值：App 才拿得到真正的数据。

## 8. 防作弊与数据可信原则

1. **不做审核工具**：不验证"是否真跑了"，截图仅被举报时人工查看
2. 排行榜只按**累计打卡次数**，不按配速/距离
3. 配速仅在个人页与打卡卡展示，无跨用户精确排名
4. 微信运动步数交叉校验仅在本地提示异常，不公开标记

## 9. 安全感与身份保护设计（核心章节）

> **前提判断**：对这个产品来说，用户不来的第一原因不是"没人"，是"来了会被看见"。
> 微信账号 = 真实社会身份，微信头像往往是本人。因此**安全感设计的优先级高于任何社交效率优化**。
> 本节所有条款为强制项，不得为了增长指标让步。

### 9.1 身份脱敏（注册环节，P0；v2.4 修订）

| # | 规则 | 说明 |
|---|---|---|
| 1 | **绝不自动填充微信头像/昵称** | P0 的真正含义是「**不替用户做决定**」：自动填充 = 逼用户在第一次打开时回答"要不要出柜"，这是最糟糕的第一道题。官方头像昵称填写能力（`chooseAvatar` + `input type="nickname"`）本身就禁止静默拉取，这条边界正好是我们想要的 |
| 2 | **默认生成彩虹几何头像** | 基于 openid 哈希生成稳定的渐变几何图形（8 色预设可换）。每人唯一、可辨识、无真实信息 |
| 3 | **昵称默认生成** | 形如「深圳 · 夜跑者 No.037」，后续可改（含选用微信昵称）。不强制先填昵称 |
| 4 | **真人头像仅主动选用，三条底线（v2.4 修订）** | ① 必须**用户主动点**（无任何引导与空态提示）② 选用前弹**一次性风险提示**（"真实照片可被截图外传、对上真人"）③ **随时可换回生成式**。选了配色 = 放弃微信头像（两者不并存）。头像存云存储 fileID（微信临时链接会失效）+ `mediaCheckAsync` 尽力校验 |
| 5 | **性别自填，默认「不愿说」**（v2.4 新增） | 微信早已不提供 gender 字段。选项：男 / 女 / 非二元 / **不愿说（默认且一级选项）**——被要求勾选本身就是压力；跑友主页只在对方愿意说时展示 |
| 6 | **手机号一律不收**（v2.4 明确） | 无账号体系需要它；它是可直接定位到真人的强实名线索；获取还按次收费。设置页「我们保存了什么」清单向用户如实列出 |
| 7 | **应用锁**（新增） | 设置 →「启动时需验证」：Soter 指纹/面容，验证通过前**不加载内容、不发请求**；设备未录入生物特征时如实提示，不给假开关 |

### 9.2 可见范围（内容环节，P0）

- 动态、打卡、照片**默认「社区内可见」**（需登录且在成员名单内），与常规社区产品"默认公开求传播"相反
- 改为公开必须由用户**逐条手动**操作，不提供"全部公开"开关
- 未登录 / 非成员访问小程序：**只能看到首页的城市数据（脱敏聚合）**，看不到任何个人内容与动态

### 9.3 分享与邀请（传播环节，P0）

| 场景 | 分享卡片内容 | 禁令 |
|---|---|---|
| 分享到微信会话 / 群 | 仅「时间 + 距离 + 城市 + 已加入人数」，如「今晚 20:00 · 深圳 · 一起跑 5KM · 已有 8 人」 | ❌ 不得出现品牌名、彩虹元素、任何身份暗示 |
| 带参太阳码（存图发送） | 同上，中性样式 | 同上 |
| 站内邀请成员 | 可含品牌视觉 | 无 |

- 分享链路**禁止携带用户昵称/头像**进入卡片（默认隐藏，用户可手动开）
- 邀请码机制：见 9.5

### 9.4 反骚扰（P0）

- **无私信、无关注**（已定），所有互动发生在公开评论区与跑友主页的**保护性动作**里
- **一键屏蔽 = 双向不可见**：被屏蔽方在信息流、场次列表、跑友推荐、搜索、跑友主页中**完全看不到**屏蔽方，反之亦然。单向屏蔽会让屏蔽变成跟踪工具。**屏蔽同时封堵评论与加油**
- 举报必须有响应：人工 24h 内处理，结果通过消息通知（privacy 类消息不显示对方信息）；举报入口在**每个用户卡片和每条内容**上，不藏在设置里；**举报两步流**（分类 + 选填说明），恶意举报影响举报者自身信用
- 评论/动态/昵称接入 `msgSecCheck`，图片接入 `security.mediaCheckAsync`（`imgSecCheck` 已下线）
- 关闭「允许陌生人互动」的人：只有互相加油过的人能评论/加油（执行点在 interact 云函数）

### 9.5 准入机制（待定，见第 14 章）

**建议采用邀请制 / 邀请码**，理由是三重的：

1. **安全感**：需要被带进来 = 天然形成"这里是我们自己人"的心理边界
2. **合规缓冲**：非完全开放注册，降低"陌生人社交"类目的认定风险
3. **质量**：极大减少恶意闯入与广告号

与冷启动的张力处理：种子期（前 200 人）通过跑团/社群定向发放，正式上线后切换为准入制；或采用「**公开浏览，参与需邀请码**」的折中。

### 9.6 线下场次安全规则（P0，对应"区别于纯线上社交"）

| 规则 | 内容 |
|---|---|
| 首次线下 | 限定**白天 + 公共场地**（如深圳湾公园），不得夜间/偏僻地点 |
| 成行人数 | 单场至少 3 人报名才允许发布为"线下场" |
| 组织者 | 首次组织线下场的成员需完成一次线上场打卡（建立最基础的行为记录） |
| 退出机制 | 报名后可无理由匿名退出，不显示"已退出"状态 |
| 位置 | 集合点只到**公园/地标粒度**，不共享实时位置、不共享个人联系方式（联系方式通过线下自愿交换） |

### 9.7 数据层面

- 用户手机号、真实姓名：**一律不采集**
- 微信 openid 与业务数据分离存储，用户可申请注销并清除全部打卡与动态
- 截图 OCR 上传前强制提示"请自行遮挡个人信息"

### 9.8 定位能力（两种，严格分开）

| 能力 | 接口 | 触发时机 | 用途 | 红线 |
|---|---|---|---|---|
| **打卡一次性定位** | `wx.getLocation({type:'gcj02'})` | 仅用户主动点击「获取当前位置」时读一次 | 判断城市归属、驱动城市点亮 | 不持续追踪、不上传轨迹；动态与榜单**只显示城市**，不展示精确坐标；用户可跳过，跳过则沿用上次城市 |
| **集合点地图选点** | `wx.chooseLocation` | 发起线下场时打开微信内置地图选点 | 返回 POI 名称 / 地址 / 经纬度，保证大家去的是同一地点 | **只存集合点**，不共享任何人的实时位置；线下场未选点不允许提交 |

> 两者均需用户手势触发，**禁止在后台或页面加载时静默调用**。
> 隐私协议表述：定位用途写「**一次性城市归属判断**」与「**集合点地图选点**」，明确写"不持续追踪、不上传轨迹、不实时共享位置"（提审与协议双处一致）。

### 9.9 安全中心（v2.0 新增，P0）

> 安全中心的每一个开关都**必须在读路径强制执行**（search / feed / interact / profile）。
> 一个看起来有保护作用、实际什么都没拦的开关，比没有开关更有害——它买到的是安心，提供不了安全。

| 模块 | 能力 | 执行点 |
|---|---|---|
| **可见范围三档** | 同城可见（默认）/ 仅互相加油过的人 / 隐身 | search 过滤（cheered 档算互相加油白名单）；feed 过滤（非 city 档不进同城流）；跑友主页同规则 |
| **一键隐身 24h** | 临时从所有推荐与搜索中消失；可提前恢复 | search / feed 全部过滤 `ghost_until`；**已加入的场次不受影响**（报名了却消失对同场的人是另一种冒犯） |
| **允许被搜索** | 关闭后搜不到昵称 | search 过滤 `searchable` |
| **动态出现在同城流** | 关闭后动态不进同城流 | feed 过滤 `allow_feed` |
| **允许陌生人互动** | 关闭后仅互相加油过的人可鼓励/评论 | interact 前置校验 `allow_cheer` |
| **品牌便签开关** | 进入时是否浮出便签（肩膀冲浪对策）+ 重新看看 | 纯客户端 |
| **黑名单** | 双向屏蔽列表 + 解除 | 见 9.4 |
| **导出我的数据** | PIPL 可携带权：一键导出自己的全部打卡与动态（JSON 到剪贴板，不过云存储、不含任何他人数据） | getMe 云函数 export 档 |
| **注销** | 真删（见 9.7）；举报记录保留 | getMe deleteAccount |

**关闭主页的呈现**：隐身中 / 可见范围非公开的用户，主页显示「**TA 关闭了主页 + 每个人都可以决定自己被谁看到**」——明说，不是 404。假装页面不存在，会让人以为 App 在删人。

## 10. 合规与隐私

### 10.1 主体与类目（决定生死，必须先确认）

| 项 | 结论 |
|---|---|
| **主体** | ⚠️ **必须企业 / 个体工商户主体**。个人主体做这个定位基本没有过审可能——「社交」类目本身不对个人开放，且个人主体无法承接 ICP 备案与内容安全责任。**这是 P0 前置条件，未解决则不应开工** |
| **类目** | 主类目选「运动 - 运动健身」；**不主动申请「社交 - 陌生人社交」**（该类目需 ICP 证 / EDI 证，审核极严且会显著放大审查力度） |
| 名称 / 简介 / 关键词 | 严格执行第 1.2 节**外层中性**原则：不出现同志、同性、les、gay、pride 等任何可被机器命中的词 |
| 提审策略 | 材料与描述主打"同城跑步打卡与约跑"，不主动强调社群属性。按此表达过审是现实可行的（同类产品有存活先例），但需预留 1–2 次驳回迭代 |

### 10.2 数据与内容

- 定位：**仅两种一次性用途，不持续追踪、不上传轨迹、不展示精确坐标**。见 9.8
- 不采集手机号、真实姓名（见 9.7）
- 需在 `app.json` 的 `requiredPrivateInfos` 中声明 `getLocation` / `chooseLocation`，提审用途写「**集合点地图选点**」「**一次性城市归属判断**」，比笼统的「用于定位」更易过审
- 用户协议 + 隐私政策：小程序常规双授权；截图上传前提示"请自行遮挡个人信息"
- UGC 审核：接入微信内容安全接口（`msgSecCheck` / `imgSecCheck`）
- 兜底：人工 24h 举报响应机制（见 9.4）

### 10.3 技术接口清单

| 能力 | 接口 | 用途 |
|---|---|---|
| 地图选点 | `wx.chooseLocation` | 发起线下场时选集合点（POI 名 / 地址 / 经纬度） |
| 一次性定位 | `wx.getLocation({type:'gcj02'})` | 打卡时读一次，判断城市归属 |
| 订阅消息 | `wx.requestSubscribeMessage` | 开始前 1h 提醒、本场结束提醒、活动取消通知 |
| 选图 | `wx.chooseMedia` | 上传成绩卡截图 |
| OCR | 云函数调用 OCR 服务 | 识别成绩卡的距离、时长、配速（版式适配层 + 置信度阈值） |
| 图片内容安全 | `security.mediaCheckAsync` | 替代**已下线**的 `imgSecCheck` |
| 文本内容安全 | `msgSecCheck`（或云调用） | 动态、昵称、队伍名检测 |
| 太阳码 | `wxacode.getUnlimited` | 队伍/场次邀请码（带参数） |
| 头像 / 昵称 | 头像昵称填写能力（`open-type="chooseAvatar"` + `input type="nickname"`） | 替代已调整的 `wx.getUserProfile`；**默认生成式身份，用户主动选用才用微信的**（三条底线，见 9.1） |
| 站内消息 | `messages` 集合 + interact 云函数 | 五类站内消息与内联操作（见 4.6）；**订阅消息**（`wx.requestSubscribeMessage`）负责服务通知，逐次授权 |

**明确不使用的能力（勿擅自引入）**：

| 能力 | 接口 | 原因 |
|---|---|---|
| 后台持续定位 | `wx.startLocationUpdateBackground` | 需类目与后台授权，推翻隐私承诺；轨迹属 PIPL 敏感个人信息 |
| 前台持续定位 | `wx.startLocationUpdate` | 本期不做轨迹记录（ADR-001） |
| 实时位置共享 / 附近的人 | — | 对社群用户构成实质安全风险 |
| 获取手机号 | `phonenumber.getPhoneNumber` | 强实名线索，无账号体系需要（9.1 #6） |

## 12. 冷启动运营（上线前 30 天）

| 阶段 | 动作 | 目标 |
|---|---|---|
| 上线前 2 周 | 从现有跑团/社群导入 50–100 名深圳种子用户进内测群 | 收集录入摩擦反馈 |
| 第 1–2 周 | 官方每天 20:00 固定场次；运营每天发 3–5 条动态；给每条打卡鼓励+评论 | 打卡率 > 40% |
| 第 3–4 周 | 组织 1 次线下约跑（深圳湾，白天公共场地）；跑友推荐位人工运营 | 首次自然约跑达成 |
| 第 5–8 周 | 促成第一批"固定跑伴"（同场 ≥ 3 次的两人组） | ≥ 10 对 |

### 12.1 北极星指标（随定位调整）

> 「让跑步不再孤单」不是一个可以用 DAU 衡量的目标。
> 打卡人数只证明"有人用"，不证明"不孤单"。

| 层级 | 指标 | 成立线 |
|---|---|---|
| **北极星** | **月度线下同跑人次**（真正见面的次数） | 深圳 ≥ 30 人次/月 |
| 核心关系指标 | **固定跑伴对数**（两人在不同场次同跑 ≥ 3 次） | ≥ 20 对 |
| 规模指标 | 同城周活跃打卡人数 | 100 人（生存线：30 人/周） |
| 健康度指标 | 次周留存 | ≥ 40% |

**判断标准**：如果打卡人数涨但线下人次为 0，说明产品退化成了一个带彩虹的跑步记录本——**定位失败**，此时应停止加功能，回到线下场景设计。

## 14. 未决问题（v1.4 重编号）

### 🔴 阻塞项（不解决不应开工）

1. **主体资格（进行中）**：已确定走**个体工商户**。⚠️ 微信官方口径不一致——有答复明确说「个人主体小程序不支持任何形式的主体变更（含变更为个体工商户）」，也有说可以。**不要赌**：直接用个体户执照注册小程序，不要先注册个人主体再变更。主体不只卡过审，也卡开发（云开发/真机/订阅消息/太阳码都依赖 AppID）
2. **准入机制**：是否采用邀请码制？建议「**公开浏览，参与需邀请码**」——兼顾安全感、合规缓冲与冷启动，代价是削弱自然增长
